1. Was ist SDD — und woher es kommt [cite: 29]

Spec-Driven Development stellt eine maschinenlesbare Spezifikation ins Zentrum des Entwicklungsprozesses. [cite: 30] Zuerst wird beschrieben, was ein System leisten soll und unter welchen Bedingungen; aus dieser Beschreibung leitet ein KI-Agent Plan, Tests und Code ab. [cite: 31, 32] Die Spezifikation ist der verbindliche Vertrag — die „Source of Truth“. [cite: 33] Code und Tests sind nachgelagerte Artefakte, die sich an ihr messen lassen müssen. [cite: 34] Der entscheidende Effekt: Der menschliche Aufwand verschiebt sich von der Implementierung hin zur präzisen Beschreibung von Anforderungen, Architektur und Akzeptanzkriterien — also dorthin, wo Fehler am billigsten zu beheben sind. [cite: 35]

Vertiefung — Einordnung [cite: 36]
SDD ist keine Erfindung von 2025, sondern eine Neuverpackung bewährter Ideen des Software-Engineerings: [cite: 36]
Contract-First-Design Die Schnittstelle (z. B. als OpenAPI/Swagger-Dokument) steht vor der Implementierung fest. [cite: 36]
Design by Contract (Bertrand Meyer, Eiffel) — Vor- und Nachbedingungen als Vertrag zwischen Komponenten. [cite: 36]
Formale Spezifikation & BDD (Z, VDM) und Behaviour-Driven Development (Gherkin/Cucumber) — Verhalten in prüfbarer Form. [cite: 36]
ADR Architecture Decision Records — bewusst dokumentierte, nachvollziehbare Entwurfsentscheidungen. [cite: 36]
Neu ist allein der Auslöser: Leistungsfähige Coding-Agenten machen es erstmals praktikabel, ausführbaren Code unmittelbar aus einer präzisen Spezifikation zu erzeugen. [cite: 36]

2. Das Problem: „Vibe Coding“ [cite: 37]

Der Begriff „Vibe Coding“ wurde Anfang 2025 geprägt. Sein Kern ist nicht bloß „einfacher Prompt, dann iterieren“, sondern dass man den generierten Code akzeptiert, ohne ihn vollständig zu lesen oder zu verstehen — man gibt sich den „Vibes“ hin und vertraut dem Modell. [cite: 38] Für schnelle Prototypen, Wegwerf-Skripte und Exploration ist das ein legitimes, oft sehr produktives Vorgehen. [cite: 39]

Bei ernsthaften, langlebigen Systemen treten jedoch typische Nachteile auf: Der Agent trifft willkürliche architektonische Entscheidungen, die Ergebnisse sind schwer reproduzierbar, es fehlt die Nachvollziehbarkeit, und der Code „kompiliert zwar, trifft aber die eigentliche Absicht nicht“. [cite: 40] Der klassische Planungs- und Reviewzyklus wird übersprungen, was Wartung und Teamarbeit erschwert. [cite: 41]

Wichtig — keine Schwarz-Weiß-Frage: Vibe Coding ist nicht per se schlecht; es ist das richtige Werkzeug für Wegwerf-Code und schnelle Experimente. SDD lohnt sich, sobald Korrektheit, Wartbarkeit, Teamarbeit, Sicherheit oder rechtliche Nachvollziehbarkeit zählen. [cite: 42]

3. Die Prinzipien des SDD [cite: 43]

  • Spezifikation als Source of Truth. Die Spec ist der maßgebliche Vertrag. Bei Abweichungen wird zuerst die Spec geprüft und angepasst, nicht ad hoc der Code. [cite: 45, 46]
  • Trennung von „Was“ und „Wie“. Der Mensch definiert das Was, der Agent übernimmt das Wie (Syntax, Boilerplate, Implementierungsdetails). [cite: 47]
  • Shift-Left der menschlichen Kontrolle. Das Review findet bei Spezifikation und Architektur statt — bevor Code entsteht. [cite: 48]
  • Leitplanken statt Determinismus. Enge Vorgaben zu Bibliotheken, Fehlerbehandlung und Namenskonventionen verkleinern den Lösungsraum. [cite: 49, 50]
  • Verifizierbarkeit durch Design. Eine Spec ist nur so gut, wie sie sich in messbare Akzeptanzkriterien übersetzen lässt. [cite: 51]
  • Nachvollziehbarkeit (Traceability). Jedes Code-Artefakt lässt sich auf ein Spec-Element zurückführen. [cite: 52]
  • Lebendes Dokument. Die Spec wird versioniert, lebt im Repository und wird über Pull Requests fortgeschrieben. [cite: 54, 55]
  • Werkzeug-Unabhängigkeit. SDD ist eine Methodik, kein Produkt. [cite: 56]
Vertiefung — „Source of Truth“ realistisch betrachtet [cite: 57]
Das Ideal lautet: bei Fehlern stets die Spec ändern und den Code neu generieren, nie umgekehrt. In der Praxis ist das eine Zielvorstellung, kein Automatismus. Generierter Code braucht weiterhin Review; eine Spec erfasst selten 100 % des Verhaltens; und das verlustfreie Regenerieren von Code aus der Spec funktioniert heute nicht zuverlässig. Wer am Code vorbei arbeitet, erzeugt „Spec-Drift“. Behandeln Sie das Prinzip daher als Disziplin, die das Team aktiv aufrechterhält. [cite: 57]

4. Das Spezifikationsdokument [cite: 58]

Eine Spec wird als maschinenlesbarer Vertrag (typischerweise Markdown) in das Projekt gelegt und dem Coding-Agenten als Kontext übergeben. [cite: 60] Das folgende Beispiel stammt aus einem Prototypen für Predictive Maintenance: Eine Maschine wird mit Sensoren nachgerüstet, ein ML-Modell bewertet ihren Zustand, und ein Industriemeister überwacht das Ergebnis. [cite: 61, 62]

Spezifikations-Beispiel (spec.md) [cite: 66, 230]

Die Spec ist zugleich Bauplan und Übergabedokument. [cite: 64]

# Feature: Predictive-Maintenance-Prototyp

## 0. Zweck & Reifegrad
PROTOTYP / Proof of Concept. Ziel ist NICHT der produktive Dauerbetrieb, sondern der Nachweis, dass sich aus Sensordaten ein brauchbares Frühwarnsignal für den Wartungsbedarf ableiten lässt. Die skalierte, produktive Umsetzung erfolgt anschließend mit externen Fachleuten. Diese Spec ist zugleich Bauplan und Übergabedokument.

## 1. Daten-Contract (Sensorik)
- Quelle: Sensor-Gateway sendet Messwerte als JSON per HTTP POST an /ingest.
- Abtastrate (Prototyp): 1 Messung pro Sekunde je Sensor.
- Felder je Nachricht:
  - machineId (string)
  - timestamp (ISO 8601, UTC)
  - vibration (number, mm/s)
  - temperature (number, °C)
  - current (number, A)
- Plausibilitätsgrenzen -- Werte außerhalb gelten als SENSORFEHLER, NICHT als Maschinenfehler:
  - temperature: -20 bis 150
  - vibration: 0 bis 50
  - current: 0 bis 100

## 2. ML-Aufgabe (bewusst einfach gehalten)
- Aufgabentyp: ANOMALIE-ERKENNUNG (unüberwacht). KEINE Ausfallvorhersage in Zeiteinheiten -- im Prototyp liegen i. d. R. noch keine echten Ausfälle als Trainingslabel vor ("Cold-Start-Problem").
- Vorgehen: Das Modell lernt das Normalverhalten aus einer störungsfreien Referenzphase und meldet Abweichungen als Anomalie-Score.
- Ausgabe je Maschine, alle 5 Sekunden aktualisiert:
  - healthScore (number, 0..1)
  - status ("ok" | "warnung" | "kritisch")
  - Schwellen: < 0.4 = ok,  0.4-0.7 = warnung,  > 0.7 = kritisch
  - dataStale (boolean) -- true, wenn seit > 30 s keine gültigen Werte kamen

## 3. Web-Oberfläche (für den Industriemeister)
- Eine Seite, Auto-Refresh alle 5 Sekunden.
- Zeigt je Maschine: Ampel (grün/gelb/rot), healthScore, Zeitpunkt der letzten Messung sowie den Verlauf der letzten 30 Minuten als einfaches Liniendiagramm.
- Bei Status "kritisch" oder dataStale: deutlich sichtbarer Warnhinweis.

## 4. Verhalten in Sonderfällen
- Datenlücke / Sensorausfall: Status NICHT auf "ok" setzen; dataStale = true.
- Sensorfehler: Messwert verwerfen, im UI als "Sensor prüfen" markieren, nicht in den healthScore einrechnen.
- Kaltstart: Status "lernt ..." anzeigen, noch keine Warnungen erzeugen.

## 5. Technische Constraints (prototyp-tauglich)
- Sprache: Python.
- ML: scikit-learn, z. B. IsolationForest -- KEIN Deep Learning.
- Backend: FastAPI; Datenhaltung: SQLite.
- Frontend: simple HTML-Seite via fetch.
- Lokal auf einem Rechner lauffähig.

## 6. Akzeptanzkriterien
- Bei Normaldaten bleibt der Status auf "ok".
- Künstliche Anomalie hebt Status nach 15 s auf "warnung".
- Abgeschalteter Sensor zeigt binnen 30 s dataStale an.

## 7. Annahmen
- Genau eine Maschine, internes Netz, ausreichend Trainingsdaten.

## 8. Bewusst NICHT im Prototyp -- Übergabe an Fachleute
- Skalierung, Zeitreihen-DB, echte Restlebensdauer-Vorhersage, Auth, Audit, Alerting.

5. Der Workflow in der Praxis [cite: 68]

Der Workflow gliedert sich in fünf Phasen: [cite: 69]

  1. Spezifizieren. Die Spec schreiben und den Agenten auf Logiklücken prüfen lassen — noch ohne Code. [cite: 71]
  2. Planen. Einen technischen Plan ableiten: Architektur, Datenmodell, Schnittstellen. [cite: 72]
  3. Zerlegen. Den Plan in kleine, einzeln testbare Aufgaben aufteilen. [cite: 73]
  4. Implementieren. Zuerst Tests aus der Spec generieren (Shift-Left), dann Code schreiben, bis die Tests grün sind. [cite: 74] Fehlermeldungen gehen zur Selbstkorrektur an den Agenten. [cite: 75]
  5. Verifizieren & Review. Prüfen, warum die Tests grün sind. Neue Regeln wandern in die Spec. [cite: 76, 77]

6. Werkzeuglandschaft [cite: 79]

Den Begriff SDD hat vor allem GitHub Spec Kit geprägt. [cite: 80] Coding-Agenten, mit denen SDD praktiziert wird, sind unter anderem Claude Code, GitHub Copilot, Gemini CLI, Cursor und Aider. [cite: 82] Entscheidend ist nicht das Produkt, sondern die Disziplin: Spezifikation zuerst, Code als Ableitung. [cite: 83]

7. Grenzen — und wann SDD sich nicht lohnt [cite: 84]

  • Overhead: Eine gute Spec zu schreiben kostet Zeit. [cite: 86]
  • Fehlbare Spec: Eine Spezifikation kann genauso unvollständig oder falsch sein wie Code. [cite: 87]
  • Restrisiko Halluzination: Auch mit Constraints kann ein Modell Fehler produzieren. [cite: 89]
  • Spec-Drift: Code und Spec laufen auseinander, wenn man am Code vorbei arbeitet. [cite: 90]
Faustregel zur Auswahl [cite: 92]
SDD lohnt sich bei langlebigen, mehrköpfigen, korrektheits- oder compliance-kritischen Projekten und beim Arbeiten in bestehenden Codebasen. Für Exploration, Lernprojekte und Einweg-Skripte genügt Vibe Coding — und ist oft schneller. [cite: 92]

8. Spezifikationen schnell erstellen: der Meta-Prompt [cite: 93]

Statt Spezifikationen mühsam selbst zu schreiben, dreht man den Spieß um und lässt sich von der KI interviewen. [cite: 94]

Du agierst ab sofort als sehr erfahrener Senior Software Architect und Product Manager. Mein Ziel ist es, nach den Prinzipien des Spec-Driven Development (SDD) zu arbeiten. Am Ende sollst du mir eine wasserdichte, maschinenlesbare Markdown-Spezifikation (spec.md) für ein Feature/Projekt schreiben, die ich direkt an einen KI-Coding-Agenten übergeben kann.

Hier ist meine noch sehr vage Idee:
[HIER DEINE IDEE EINTRAGEN, z. B. "Ich brauche ein internes Dashboard, in dem Mitarbeiter Urlaubsanträge einreichen und Vorgesetzte sie genehmigen."]

WICHTIGE REGEL: Schreibe die Spezifikation noch NICHT.

Bevor wir sie erstellen, musst du alle Unklarheiten beseitigen. Stelle mir eine strukturierte, nummerierte Liste der 10 bis 14 wichtigsten Fragen.
Gruppiere sie in folgende Kategorien:
1. Geschäftslogik & Core-Feature-Verhalten
2. Edge Cases (unerwartetes Verhalten, Fehler, Nebenläufigkeit)
3. Security, Authentifizierung & Berechtigungen
4. Technische Constraints (Stack, Datenbank, APIs)
5. Nicht-funktionale Anforderungen (Performance, Skalierung, Logging, Datenschutz)
6. Testing & Akzeptanzkriterien

Stelle präzise, technische Fragen. Biete bei komplexen Punkten direkt 2 bis 3 Best-Practice-Optionen (A, B, C) an, aus denen ich wählen kann.

Warte nach deinen Fragen auf meine Antworten. Wenn meine Antworten weitere Lücken aufwerfen, hake nach. Deine Einschätzung "keine Lücken mehr" ist eine Heuristik, keine Garantie -- bleibe daher kritisch. Erst wenn du hinreichend sicher bist, werde ich sagen: "Erstelle jetzt die spec.md".

So geht es nach dem Prompt weiter [cite: 97]

Beantworten: kurz und knapp auf die Fragen antworten. [cite: 98]
Nachschärfen: eventuelle Rückfragen der KI klären. [cite: 99]
Generieren: den finalen Befehl geben: „Perfekt. Erstelle nun die finale spec.md...“ [cite: 100]

10. Glossar [cite: 117]

  • Spec-Driven Development (SDD): Methodik, die eine maschinenlesbare Spezifikation ins Zentrum stellt. [cite: 118]
  • Vibe Coding: Generierten Code akzeptieren und iterieren, ohne ihn vollständig zu durchdringen. [cite: 119]
  • Source of Truth: Die Spezifikation als einzige verbindliche Referenz. [cite: 120]
  • Shift-Left: Qualitätssicherung früh im Prozess verankern (Review bei Spec/Architektur). [cite: 121]
  • Traceability: Jedes Code-Artefakt lässt sich auf ein Spec-Element zurückführen. [cite: 123]
  • Constitution: Projektweite Grundregeln, die über einzelnen Specs stehen. [cite: 127]
  • Spec-Drift: Auseinanderlaufen von Spezifikation und Code. [cite: 129]

Erste Schritte: SDD ist iterativ, nicht Wasserfall [cite: 139]

Niemand schreibt vor dem ersten Tastendruck eine perfekte, fertige Spezifikation. Genau das wäre nicht SDD, sondern Wasserfall. [cite: 134] Die Spezifikation wächst mit dem Projekt: Man startet mit einem Skelett und füllt es Schritt für Schritt. [cite: 137]

“Altes Software-Dev” (Wasserfall) [cite: 143] So ist SDD gemeint (iterativ) [cite: 143]
Erst das komplette Dokument, dann Code Dünne Spec, kurzer Durchlauf, dann nachschärfen
Die Spec ist fertig und unveränderlich Die Spec ist ein lebendes Dokument
Ein großer Wurf Viele kleine, vollständige Schnitte

Faustregel für den Einstieg: Stabiles früh, Volatiles spät. Vorab gehört, was billig zu denken und teuer zu ändern ist. Wachsen darf, was man ohnehin erst später genauer weiß. [cite: 148, 149]

1. Das Fundament: die Spec ins Projekt legen [cite: 167]

Die Spezifikation ist die „Source of Truth“. Sie gehört als Datei ins Projekt — nicht in den Chatverlauf. [cite: 168] Daneben braucht das Werkzeug dauerhafte Projektregeln (die „Constitution“), so muss man sich nicht in jeder Sitzung wiederholen. [cite: 170, 171]

# Inhalt für CLAUDE.md oder CONVENTIONS.md
# Projekt: Predictive-Maintenance-Prototyp
- Verbindliche Spezifikation: siehe spec.md (Source of Truth).
- Sprache: Python. Stil: einfach, gut kommentiert, prototyp-tauglich.
- Stack laut spec.md: FastAPI, scikit-learn, SQLite. Kein Deep Learning.
- Regel: Neue Anforderungen zuerst in spec.md aufnehmen, dann umsetzen.
- Vor groesseren Aenderungen kurz den Plan erlaeutern.

Tipp: Initialisiere Git und committe nach jeder Phase. [cite: 173, 174]

git init
git add spec.md CLAUDE.md
git commit -m "chore: Spezifikation und Projektregeln"

2. Spec prüfen und Plan erzeugen — noch ohne Code [cite: 176]

Das ist der „Shift-Left“-Moment: Bevor eine Zeile Code entsteht, lässt du das Modell die Spezifikation auf Lücken prüfen. Arbeite dafür in einem Modus, der nur liest und nichts verändert. [cite: 177, 178]

Prompt:
Lies @spec.md und @CLAUDE.md. Du bist erfahrener Senior-Entwickler. Prüfe die Spezifikation auf Architektur- und Logiklücken, BEVOR wir Code schreiben. Stelle mir gezielte Rückfragen zu allem, was unklar oder widersprüchlich ist. Schreibe noch keinen Code.

Beantworte die Rückfragen knapp. Tauchen dabei echte Lücken auf, ergänze sie in spec.md — nicht im Chat. [cite: 180] Danach lässt du den Plan erstellen: [cite: 181]

Prompt:
Erstelle aus @spec.md einen technischen Plan und speichere ihn als plan.md:
Projektstruktur (Dateien/Module), Datenfluss, gewählte Bibliotheken und kurze Begründungen.
Halte dich an die Constraints in spec.md. Noch kein Implementierungscode.

3. In kleine Aufgaben zerlegen [cite: 301]

Aus dem Plan wird eine Aufgabenliste (tasks.md). [cite: 302]

Prompt:
Leite aus @plan.md eine Aufgabenliste ab und speichere sie als tasks.md:
kleine, einzeln testbare Schritte in sinnvoller Reihenfolge, jede mit einem Satz Ziel.

4. Implementieren — Tests zuerst [cite: 314]

Jetzt darf der Agent Dateien anlegen und Befehle ausführen (z.B. im Agent-Modus von Continue). Die SDD-Reihenfolge lautet: erst die Tests aus den Akzeptanzkriterien, dann der Code. [cite: 315, 316]

Schritt 1 — Tests, die zunächst fehlschlagen: [cite: 317]

Prompt:
Wir arbeiten @tasks.md Schritt für Schritt ab. Beginne mit den Tests. Schreibe auf Basis der Akzeptanzkriterien in @spec.md (Abschnitt 6) pytest-Tests, die das Verhalten prüfen und zunächst fehlschlagen. Erkläre kurz, was jeder Test prüft. Schreibe noch keinen Implementierungscode.

Schritt 2 — Code, bis die Tests grün sind: [cite: 319]

Prompt:
Implementiere jetzt den Code, bis alle Tests grün sind. Halte dich strikt an die Constraints in @spec.md Abschnitt 5 (Python, FastAPI, scikit-learn IsolationForest, SQLite). Führe die Tests aus und zeig mir das Ergebnis. Schlagen Tests fehl, korrigiere und wiederhole.

Schritt 3 — testen ohne echte Maschine: [cite: 323]

Prompt:
Erzeuge ein Skript simulate_sensor.py, das jede Sekunde plausible Messwerte an /ingest sendet.
Mit dem Schalter --anomalie steigt die Vibration langsam an, sodass der Status auf warnung/kritisch wechselt. So kann ich die Akzeptanzkriterien von Hand prüfen.

5. Verifizieren & weiterentwickeln [cite: 327]

Neue Wünsche oder gefundene Fehler kommen ZUERST in spec.md — nie als formloser Zuruf an den Code. [cite: 330]

Prompt-Beispiel für Änderung:
@spec.md wurde geändert (Abschnitt 3: Maschinen-ID im Titel der Web-Oberfläche).
Passe Implementierung UND Tests entsprechend an und führe die Tests aus.

Häufige Stolpersteine [cite: 335]

  • Blind „Accept“ klicken. Diffs immer lesen. [cite: 336]
  • Grün ≠ richtig. Tests können bestehen, weil sie abgeschwächt wurden. [cite: 337]
  • Kontext überladen. Nur relevante Dateien anhängen. [cite: 338]
  • Sensible Daten. Keine echten Betriebsdaten an Cloud-Modelle. [cite: 339]

- **Sensorfehler** (Wert außerhalb der Plausibilitätsgrenzen): Messwert verwerfen, im UI als „Sensor prüfen“ markieren, nicht in den `healthScore` einrechnen. [cite: 271, 272]
- **Kaltstart** (Modell noch nicht angelernt): Status `"lernt …"` anzeigen, noch keine Warnungen erzeugen. [cite: 273, 274]

## 5. Technische Constraints (prototyp-tauglich) [cite: 275]
- **Sprache:** Python. [cite: 276]
- **ML:** scikit-learn, z. B. `IsolationForest` — kein Deep Learning im Prototyp. [cite: 277]
- **Backend:** FastAPI. **Datenhaltung:** SQLite (eine Datei, kein DB-Server). [cite: 278]
- **Frontend:** eine einfache HTML-Seite, die das Backend per `fetch` abfragt. [cite: 279]
- Alles lokal auf einem Rechner lauffähig, keine Cloud-Abhängigkeit. [cite: 280]

## 6. Akzeptanzkriterien (Prototyp gilt als erfolgreich, wenn …) [cite: 281]
1. Bei eingespielten Normaldaten bleibt der Status stabil auf `ok`. [cite: 282]
2. Eine künstlich erzeugte Auffälligkeit (z. B. steigende Vibration) hebt den Status innerhalb von 15 s auf `warnung`/`kritisch`. [cite: 283, 284]
3. Bei abgeschaltetem Sensor zeigt das UI binnen 30 s `dataStale` an. [cite: 285]
4. Der Industriemeister deutet den angezeigten Zustand ohne Erklärung richtig. [cite: 286]

## 7. Annahmen (explizit, damit sie überprüfbar bleiben) [cite: 287]
- Genau eine Maschine; Mehrmaschinen-Betrieb erst in der Produktivversion. [cite: 288]
- Läuft im geschützten internen Netz → keine Authentifizierung/Verschlüsselung im PoC. [cite: 289]
- Eine ausreichend lange störungsfreie Referenzphase zum Anlernen existiert. [cite: 290]
- Datenmengen sind klein genug für SQLite und einen einzelnen Prozess. [cite: 291]

## 8. Bewusst NICHT im Prototyp — Übergabe an Fachleute [cite: 292]
- Skalierung auf viele Maschinen, Hochverfügbarkeit, Zeitreihen-Datenbank. [cite: 293]
- Echte Restlebensdauer-Vorhersage auf Basis gelabelter Ausfälle. [cite: 294]
- Authentifizierung, Rollen, Audit, Alarmierung per E-Mail/SMS. [cite: 295]
- Modell-Monitoring, Drift-Erkennung, regelmäßiges Re-Training. [cite: 296]
- OT-/Sicherheitsanforderungen (Trennung vom Produktionsnetz, einschlägige Normen). [cite: 297]

Vertiefungen & Hintergrundwissen

Vertiefung — Was eine gute KI-/ML-Prototyp-Spec ausmacht [cite: 67]
ML-Aufgabe präzise benennen: Anomalie-Erkennung ist nicht dasselbe wie Ausfallvorhersage. Wer das offenlässt, bekommt vom Agenten womöglich etwas ganz anderes als gemeint. [cite: 67]
Cold-Start ehrlich behandeln: Predictive Maintenance bräuchte eigentlich echte Ausfalldaten zum Lernen, die im Prototyp fast nie vorliegen. Die Spec macht aus dieser Not eine bewusste Entscheidung: unüberwachte Anomalie-Erkennung auf Basis des Normalverhaltens. [cite: 67]
Daten-Contract ist das Fundament: Format, Abtastrate, Einheiten und Plausibilitätsgrenzen. Ein ML-System ist nur so gut wie die Klarheit über seine Eingangsdaten — „garbage in, garbage out“. [cite: 67]
Sensorfehler ≠ Maschinenfehler: Diese Unterscheidung entscheidet, ob das Frühwarnsystem vertrauenswürdig ist. Ein defekter Sensor darf keinen Maschinenalarm auslösen — und umgekehrt. [cite: 67]
Verständlichkeit für den Nutzer: Der Industriemeister ist kein Data Scientist. Eine Ampel, die er ohne Schulung deuten kann, ist mehr wert als ein präziser, aber unverständlicher Score. [cite: 67]
Annahmen und Scope explizit machen: Gerade weil später Fachleute übernehmen, ist die Spec die Übergabestelle. Die Abschnitte „Annahmen“ und „Bewusst NICHT im Prototyp“ verhindern, dass ein Proof of Concept versehentlich für ein fertiges Produkt gehalten wird. [cite: 67]
Achtung — Grenzen der autonomen Fehlerbehebung [cite: 78]
Ein Agent kann Tests auch „grün“ bekommen, indem er Assertions abschwächt oder Sonderfälle umgeht, statt das Problem zu lösen. [cite: 78] Das Review muss daher prüfen, ob die Tests das richtige Verhalten erzwingen — nicht nur, ob sie bestehen. [cite: 78] Begrenzen Sie zudem die Zahl der Selbstkorrektur-Schleifen, um Endlos-Iterationen zu vermeiden. [cite: 78]

9. Der SDD-Prozess von der Idee zum fertigen Feature

Der Spec-Driven-Development-Ablauf lässt sich als eine Kette aus fünf Phasen beschreiben, die jeweils ein überprüfbares Zwischenergebnis erzeugen[cite: 101, 102]. Über allen Phasen liegt dabei die übergeordnete Constitution (z. B. die `CLAUDE.md` bzw. `CONVENTIONS.md` im Tutorial)[cite: 103].

Aus der ursprünglichen Idee entsteht in der Phase „Spezifizieren" die Datei `spec.md`, die als Source of Truth den verbindlichen Vertrag bildet[cite: 104]. Vor der ersten Zeile Code steht ein menschliches Review, das die Spezifikation auf Architektur- und Logiklücken prüft (Shift-Left)[cite: 105]. Werden Lücken gefunden, fließt die Korrektur direkt zurück in die Spec und nicht erst in eine spätere Phase[cite: 106].

Erst nach Freigabe leitet die Phase „Planen" daraus `plan.md` ab (Architektur, Stack, Datenmodell) und die Phase „Zerlegen" erzeugt die `tasks.md` (kleine, einzeln testbare Aufgaben)[cite: 107]. In der Phase „Implementieren" werden zuerst die Tests aus der Spezifikation erzeugt — sie schlagen zunächst fehl — und anschließend so viel Code geschrieben, bis die Tests grün sind[cite: 108]. Schlägt ein Test fehl, geht die Fehlermeldung zurück an den Agenten, der den Code anpasst[cite: 109]. Diese Test-Korrektur-Schleife läuft innerhalb der Implementierung und betrifft nur den Code, nicht die Anforderungen[cite: 110].

Die Phase „Verifizieren & Review" prüft danach nicht nur, dass die Tests grün sind, sondern warum[cite: 111]. Hier zeigt sich die zentrale SDD-Regel als wichtige Rückkopplung: Jede neue Regel und jeder gefundene Fehler wird zuerst in `spec.md` aufgenommen — die Abläufe führen deshalb stets zurück zur Phase „Spezifizieren", nie direkt zum Code[cite: 112]. Erst wenn das Feature abgenommen ist, endet der Durchlauf[cite: 113].

Zusammenfassend gibt es drei kritische Rückkopplungen im Prozess: erstens das Review vor dem Code, zweitens die Test-Korrektur-Schleife in der Implementierung und drittens die übergeordnete Schleife, die jede Änderung über die Spezifikation führt[cite: 116].

Ergänzende Prinzipien & Einstiegshilfen

“Altes Software-Dev” (Wasserfall) [cite: 143] So ist SDD gemeint (iterativ) [cite: 143]
Erst das komplette Dokument, dann Code [cite: 143] Dünne Spec, kurzer Durchlauf, dann nachschärfen [cite: 143]
Die Spec ist fertig und unveränderlich [cite: 143] Die Spec ist ein lebendes Dokument [cite: 143]
Vollständigkeit vor dem ersten Schritt [cite: 143] Nur so viel wie für den nächsten Schritt nötig [cite: 143]
Ein großer Wurf [cite: 143] Viele kleine, vollständige Schnitte [cite: 143]
Merksatz: Just enough spec — so viel Spezifikation, wie für den nächsten kleinen Schritt nötig ist, nicht mehr. [cite: 145] Die Iterationseinheit ist die Spec, nicht der Code. [cite: 147]
Faustregel für den Einstieg: Stabiles früh, Volatiles spät [cite: 148, 149]
Vorab gehört, was billig zu denken und teuer zu ändern ist. Wachsen darf, was man ohnehin erst später genauer weiß. [cite: 149]
Früh festlegen: Der ML-Aufgabentyp (hier Anomalie-Erkennung statt Ausfallvorhersage), der Daten-Contract und ein bis zwei Akzeptanzkriterien. [cite: 149]
Später wachsen lassen: Konkrete Schwellenwerte, Feinheiten und Sonderfälle. [cite: 149]

So fängst du konkret an [cite: 150]

  • Mit einem Skelett starten: Zweck, Daten-Contract und eine einzige Akzeptanzbedingung genügen. [cite: 151]
  • Den ersten kleinen Schnitt bauen — ein vollständiger, kurzer Durchlauf wie im Tutorial. [cite: 152]
  • Den laufenden Prototyp „fragen“, was als Nächstes in die Spec muss — und die Spec ergänzen. [cite: 153]

## Arbeitsweise, die ich erwarte [cite: 205]
- Bei größeren Schritten zuerst kurz den **Plan** erläutern, dann umsetzen. [cite: 206]

- In **kleinen, einzeln testbaren Schritten** entlang `tasks.md` arbeiten. [cite: 208]
- Tests selbst ausführen und das Ergebnis zeigen. Änderungen als nachvollziehbare Diffs halten. [cite: 209]
